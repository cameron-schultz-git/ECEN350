2. **Q2:** show the full processor runs Test Program 1 correctly.
3. **Q3:** add a new instruction (MOVZ), write a program that uses it, and show both programs pass.

Q1 and Q2 needed no code changes, because the prelab already passed. Q3 is the real work.

### 1.2 What MOVZ does

`MOVZ Xd, #imm16, LSL #shift` means "**mov**e a 16-bit number into Xd, shifted left by 0, 16, 32 or 48, and **z**ero every other bit".

```
MOVZ X9, 0x1234, LSL 48   →   X9 = 0x1234_0000_0000_0000
MOVZ X9, 0x1234, LSL 16   →   X9 = 0x0000_0000_1234_0000
```

Think of the 64-bit register as four 16-bit slots. MOVZ fills one slot and clears the other three.

ARM has no instruction that loads a full 64-bit constant (an instruction is only 32 bits). Real code uses MOVZ for the first slot and **MOVK** ("keep") for the rest. MOVK changes one slot and leaves the others alone. We only have MOVZ, so we use ORR to combine the slots (see 1.4).

### 1.3 The MOVZ instruction format (IM format)

```
 31        23 22 21 20                5 4     0
+------------+-----+-------------------+-------+
| 110100101  | hw  |    MOV_immediate  |  Rd   |
+------------+-----+-------------------+-------+
   9 bits     2 bits      16 bits        5 bits
```

- **hw** ("halfword") picks the slot: 00 → LSL 0, 01 → LSL 16, 10 → LSL 32, 11 → LSL 48. The shift is always `16 × hw`.
- The control unit sees bits 31:21 as the opcode, which is `110100101` followed by the two hw bits. That is why the opcode pattern is `110100101??`: **one instruction, 4 opcodes**, just like CBZ has 8.

### 1.4 Why ORR is needed to build the constant

The target is `0x1234_5678_9abc_def0`. If we did four MOVZs into X9, each one would wipe out the last, and X9 would end as `0x0000_0000_0000_def0`. So:

1. MOVZ the top slot straight into X9.
2. For each other slot, MOVZ it into a scratch register (X10), then `ORR X9, X9, X10`.

ORR works here because the slots never overlap: each MOVZ has zeros everywhere except its own 16 bits, so OR just "pastes" them together.

### 1.5 Where to do the shift — the key design decision

The datapath has to make the value `imm16 << (16 × hw)` and get it into Rd. Look at what's already there:

- The **sign extender** already pulls immediate fields out of the instruction and shifts them (CB and B shift left 2).
- The **ALU** has a **PassB** operation that outputs input B unchanged (CBZ uses it).
- The **ALUSrc mux** already sends the immediate to ALU input B.
- The **MemtoReg mux** already sends the ALU result to the register file.

So if the sign extender produces the shifted value, the rest of the path already exists: **sign extender → ALUSrc mux → ALU (PassB) → MemtoReg mux → Rd.** No new wires or muxes are needed.

The one catch: SignOp is 2 bits, and all 4 codes (I, D, CB, B) are used. So SignOp grows to 3 bits, and MOVZ gets `100`.

**The other option** (worth knowing if the TA asks): leave SignOp alone and add a "shift B by 16 × hw" operation to the ALU. That needs a new ALUOp code, and the hw bits must be routed to the ALU. That means a new port on the ALU, which is more wiring. Both designs work.

## Part 3 — The code changes, line by line

Each section is one `_q3` file, compared with its prelab version.

### 3.1 SignExtender_q3.v

```verilog
`define Itype    3'b000
`define Dtype    3'b001
`define CBtype   3'b010
`define Btype    3'b011
`define MOVZtype 3'b100
```

The old codes keep their values, just with a 0 in front (`01` → `001`). That keeps every old instruction working.

```verilog
input      [2:0]  SignOp
```

The port is now 3 bits. **Every** place that connects to SignOp has to change width too (the control output, the top-level wire, the testbench). If one is missed, Verilog quietly drops or pads the top bit. That would be the same kind of silent bug as the prelab's `ALUop` typo.

```verilog
`MOVZtype:
  case (Instruction[22:21])                                 // hw = which 16-bit slot
    2'b00:   SignExOut = {48'b0, Instruction[20:5]};        // LSL 0
    2'b01:   SignExOut = {32'b0, Instruction[20:5], 16'b0}; // LSL 16
    2'b10:   SignExOut = {16'b0, Instruction[20:5], 32'b0}; // LSL 32
    default: SignExOut = {Instruction[20:5], 48'b0};        // LSL 48
  endcase
```

- **A `case` inside a `case`:** the outer case picks the format, and the inner one picks the slot using hw.
- **`{a, b, c}` is concatenation:** the pieces are glued together, leftmost piece in the highest bits. Putting `16'b0` on the right of the immediate is the same as shifting it left 16. Each line adds up to 64 bits (e.g. 32 + 16 + 16).
- **The inner `default`** covers hw = 11 and also makes sure every path assigns SignExOut, so no latch is made.
- `Instruction` here is only bits 25:0 of the real instruction (the top level passes `instruction[25:0]`). Bits 22:21 and 20:5 are in that range, so no port change was needed.

An equivalent one-liner would be `SignExOut = {48'b0, Instruction[20:5]} << {Instruction[22:21], 4'b0};`. `{hw, 4'b0}` is `hw × 16`. The case version is easier to read in a demo and maps directly to 4 mux inputs.

### 3.2 SingleCycleControl_q3.v

```verilog
output reg [2:0] SignOp,
```

Widened, and every `SignOp = 2'b..` in every arm is now 3 bits (`3'b001`, `3'bxxx`, ...).

```verilog
`OPCODE_MOVZ:
  begin
     Reg2Loc      = 1'bx;     // Read data 2 is not used
     ALUSrc       = 1'b1;     // ALU B = the shifted immediate
     MemtoReg     = 1'b0;     // write the ALU result into Xd
     RegWrite     = 1'b1;     // yes, write Xd
     MemRead      = 1'b0;
     MemWrite     = 1'b0;
     Branch       = 1'b0;
     Uncondbranch = 1'b0;
     ALUOp        = 4'b0111;  // PassB
     SignOp       = 3'b100;   // MOVZ
  end
```

Work it out the same way as the prelab rows. Ask what MOVZ needs:

- The value comes from the immediate, so **ALUSrc = 1**.
- The ALU must not change it, so **PassB**.
- It is written to a register, so **MemtoReg = 0** (take the ALU result) and **RegWrite = 1**.
- No memory and no branch, so **0s**. These are never X, for the same safety reasons as the prelab.
- Read data 2 is never used, so **Reg2Loc = X**.

`` `OPCODE_MOVZ `` was already defined as `11'b110100101??` in the prelab, but there was no arm for it, so it fell to the default. Adding the arm is all that "turns it on".

**Read register 1 during MOVZ:** the register file always reads Rn = bits 9:5. For MOVZ those bits are part of the immediate, so it reads some random register. That's harmless: PassB ignores ALU input A.


That is the only functional change. The SignExtender and SC_Control instances connect `.SignOp(SignOp)` by name, so they pick up the new width automatically.

### 3.4 InstructionMemory_q3.v

```verilog
63'h034: Data = 32'hD2E24689;   // MOVZ X9, 0x1234, LSL 48
...
63'h054: Data = 32'hF84283EA;   // LDUR X10, [XZR, 0x28]
```

Each `case` label is an address, and the value is the instruction stored there. Addresses go up by 4 because every instruction is 4 bytes. Program 2 starts at 0x34, the first free address after Program 1.

**How to encode an instruction by hand** (do this for any one if the TA asks):

| Instruction | Fields | Hex |
| --- | --- | --- |
| `MOVZ X9, 0x1234, LSL 48` | `110100101` `11` `0001001000110100` `01001` | `D2E24689` |
| `MOVZ X10, 0x5678, LSL 32` | `110100101` `10` `0101011001111000` `01010` | `D2CACF0A` |
| `MOVZ X10, 0x9abc, LSL 16` | `110100101` `01` `1001101010111100` `01010` | `D2B3578A` |
| `MOVZ X10, 0xdef0, LSL 0` | `110100101` `00` `1101111011110000` `01010` | `D29BDE0A` |
| `ORR X9, X9, X10` | opcode `10101010000`, Rm `01010`, shamt `000000`, Rn `01001`, Rd `01001` | `AA0A0129` |
| `STUR X9, [XZR, 0x28]` | opcode `11111000000`, imm9 `000101000`, op `00`, Rn `11111`, Rt `01001` | `F80283E9` |
| `LDUR X10, [XZR, 0x28]` | opcode `11111000010`, imm9 `000101000`, op `00`, Rn `11111`, Rt `01010` | `F84283EA` |

Write the fields out in a row, regroup them into 4-bit nibbles from the left, and convert each nibble to hex. For example:

```
110100101 11 0001001000110100 01001
= 1101 0010 1110 0010 0100 0110 1000 1001
=   D    2    E    2    4    6    8    9
```

### 3.5 SingleCycleProcTest_q3.v

```verilog
#1
  Reset = 1; startPC = 64'h34;
@(posedge CLK);
@(negedge CLK);
@(posedge CLK);
Reset = 0;
```

This copies how Program 1 starts. Reset is held across two rising edges, so the PC is sure to load 0x34.

> **Why it's OK that the instruction at 0x34 runs during reset:** while Reset is high, the PC sits at 0x34 and the MOVZ there executes every cycle. It writes the same value to X9 each time, so running it 2 or 3 times gives the same result. That's also why PC 0x34 and 0x38 don't appear in the printed `CurrentPC:` trace. The loop only prints after it starts clocking.

```verilog
while (currentPC < 64'h4c) begin @(posedge CLK); @(negedge CLK); ... end
passTest(MemtoRegOut, 64'h123456789abcdef0, "Program 2: X9 built by MOVZ", passed);
```

The loop clocks the processor until the PC reaches 0x4C. It checks at the negative edge, mid-cycle, when the combinational logic has settled. At that point the last ORR is the current instruction, so MemtoRegOut is its ALU result: the finished X9. The testbench can only see the processor's ports (`currentpc`, `MemtoRegOut`), not the registers directly. That's why it checks values as they pass through MemtoRegOut.

The second loop runs to 0x54 and checks the LDUR's MemtoRegOut, which is the value read from memory.

```verilog
allPassed(passed, 3);
```

There are now 3 `passTest` calls (1 from Program 1, 2 from Program 2).

### 3.6 SingleCycleControlTest_q3.v

- `wire [2:0] SignOp`, `reg [2:0] exp_SignOp`, the `setExpected` input, and the `3'bxxx` don't-care check are all widened.
- **New MOVZ block:** loops `dc` over 0–3 and sets `opcode = {9'b110100101, dc[1:0]}`, covering all 4 hw values.
- **`isSupported`** gains `op[10:2] == 9'b110100101`, so the random test won't pick a MOVZ and expect zeros.
- **The hand-picked "BAD MOVZ" test became "BAD MOVK"** (`11110010100`). MOVZ isn't bad anymore. MOVK differs from it in one opcode bit, which makes it a good near-miss test.
- 50 + 4 = 54 supported tests, + 5 hand-picked + 10 random = **69 tests**.

## Part 4 — Following MOVZ through the processor

### MOVZ X9, 0x1234, LSL 48 at PC 0x34 — `D2E24689`

```
110100101 | 11 | 0001 0010 0011 0100 | 01001
opcode      hw   imm16 = 0x1234        Rd = 9
```

1. `opcode` = Instruction[31:21] = `11010010111` matches `110100101??` → control: ALUSrc=1, ALUOp=PassB, RegWrite=1, MemtoReg=0, SignOp=100.
2. **Sign extender:** hw = `11`, so `{0x1234, 48'b0}` = `0x1234000000000000`.
3. **ALUSrc mux:** ALU B = extimm. **ALU:** PassB, so aluout = `0x1234000000000000`.
4. **MemtoReg mux:** picks aluout. On the falling edge, X9 = `0x1234000000000000`.
5. **NextPC:** Branch = Uncondbranch = 0, so PC = 0x38.

### ORR X9, X9, X10 at PC 0x3C — `AA0A0129`

1. R-type: Reg2Loc=0, so Read register 2 = Rm = X10. ALUSrc=0, ALUOp=OR.
2. regoutA = X9 = `0x1234000000000000`, regoutB = X10 = `0x0000567800000000`.
3. aluout = `0x1234567800000000` → written to X9.

### STUR X9, [XZR, 0x28] then LDUR X10, [XZR, 0x28]

1. STUR: Reg2Loc=1, so Read register 2 = Rt = X9, and regoutB = `0x123456789abcdef0`. ALU: 0 + 0x28 = 0x28. On the rising edge, data memory writes the 8 bytes at 0x28–0x2F (big-endian: 0x12 goes in 0x28).
2. LDUR: same address. MemRead=1 and MemtoReg=1, so MemtoRegOut = memory[0x28] = `0x123456789abcdef0` → written to X10.

**Why 0x28 is a good address:** Program 1 uses 0x00–0x27 (five 8-byte values), so 0x28 is the next free 8-byte slot, and it starts as `x`. If the store failed, the load would return `x`, never the right answer by accident.

## Part 5 — Questions the TA might ask

| Question | Answer |
| --- | --- |
| Why did SignOp need a third bit? | All four 2-bit codes were already used by I, D, CB and B. |
| Why PassB and not ADD for MOVZ? | ADD would add ALU input A, which is a random register (bits 9:5 are part of the immediate). PassB ignores A. I tested this: with ADD, the result is `x`. |
| Why not just MOVZ four times into X9? | MOVZ zeros the other 48 bits, so each one would erase the previous. ORR combines them since the slots don't overlap. (A real ARM program would use MOVK.) |
| Why is Reg2Loc a don't care for MOVZ? | Read data 2 is not used (ALUSrc = 1 picks the immediate, and nothing is stored). |
| Did you have to change the ALU or add a mux? | No. Sign extender → ALUSrc mux → ALU PassB → MemtoReg mux → register file already exists. Only SignOp's width changed in the top level. |
| How do you know Program 1 still works? | The testbench runs Program 1 first, unchanged, and it still passes. |
| How does the test know the store worked? | Address 0x28 starts as `x`. The LDUR only returns the right value if STUR wrote it. |
| What does a garbled opcode do? | Falls to the default: all control signals 0, so it acts as a NOP (PC + 4, nothing written). |
| Why is the register file written on the falling edge? | So the value is written in the middle of the cycle, after the result has settled, and before the next instruction reads it in the next cycle. |
| What's the critical path of a single-cycle CPU? | LDUR: instruction memory → register file → ALU → data memory → MemtoReg mux → register file. The clock must be slow enough for the slowest instruction. That's the main drawback of single cycle. |
| What happens if you hit an address with no instruction? | InstructionMemory returns `x`. The opcode matches nothing, so the control outputs 0s (NOP). |
| How many cycles does the whole test take? | About 80 cycles (9,600 ns ÷ 120 ns), under the 255-cycle watchdog. |

## Quick syntax reference (new in this lab)

See the end of [prelab-explainer.md](prelab-explainer.md) for the full table. New or more important here:

| Syntax | Meaning |
| --- | --- |
| `{16'b0, x[20:5], 32'b0}` | concatenation; zeros on the right = shift left |
| `{N{bit}}` | replication: `bit` repeated N times (used for sign extension) |
| `case` inside a `case` | nested choice; each inner case needs its own `default` / `endcase` |
| `[2:0]` vs `[1:0]` | 3-bit vs 2-bit bus. Mismatched widths are silently padded or cut, so change them everywhere |
| `{9'b110100101, dc[1:0]}` | builds an opcode from a fixed part and a loop counter |
| `63'h034:` in InstructionMemory | a case label: "when Address is 0x34" |
| `passTest(actual, expected, name, passed)` | given task: prints passed/failed and counts passes |
